# 01｜强制修复要求

本页是针对审查快照的新任务要求。代码形状与数据结构由实现者设计；每条均要有可拒绝错误行为的测试。审查发现的可达错误路径不等于所有错误都已在用户机器实机复现，不要虚构事故次数。

## R1-L：生命周期必须在故障情况下仍控制实例数量

### L1. 先止血，再启动

暂停本项目旧 hub/watchdog/自动重拉任务，先核验 PID、创建时间、父子关系、实例目录及启动标记。只停止确认归属本轮的实例；用户 PCL2/正常客户端、生产世界和无关 Java/Gradle 不在清理范围。归属不明须拒绝自动处理，禁止按 java/javaw/KnotClient 名称批量杀进程。

本机本轮最多一套测试 server 和一套 Bob client，包括启动中、未登录、无响应实例。编译任务与 GameTest 的独立服务器须在各自声明时段计入资源协调，不能借另一目录、端口、run_id 绕开限制。真实客户端必须等待测试服务器已验证可用再启动。

### L2. 解决“进程已生成但状态没写下”的崩溃窗口

现有 `_spawn` 是先 Popen、再枚举、再落 state；文件锁不能消除调用者崩溃后留下的子进程。

实现者自行选择操作系统进程托管、持久化启动意图/保留位与可恢复 marker 等组合。必须满足：
- 任何可能创建子进程的步骤之前，启动意图已经能被后继协调者识别；未完成记录仍占配额。
- 后继 start 在创建新进程前，要核对本轮稳定命名空间中的所有实例与未决启动，不仅查 state 中的单一 PID。
- 管理器在创建前、创建后但登记前、登记后但就绪前崩溃，均只能接管原实例、确认清理后重建，或阻断；不能重复启动。
- 已失去记录的本轮进程仍能被发现。多个本轮实例、陌生占用、识别权限不足不能被解释为“空环境”。
- 不能只凭 `RCON list` 有 Bob 或日志曾出现 ready，便声称当前 PID/会话已就绪；将就绪信号对应到本次启动实例。

### L3. 损坏/缺失与健康空状态必须分开

状态文件格式损坏、I/O/权限错误、枚举失败、失败计数文件损坏、部分写入都 fail-closed。首次真正空环境可以初始化，但必须有完整进程/资源枚举作为依据；不能把所有读取异常吞掉变成 `{}`。

状态发布要原子且具有可恢复的中间态。只读 status 不得绕过锁改写有竞争的状态。所有影响配额的写操作必须受同一跨进程互斥保护。

PID + 创建时间 + 本轮标记都核验。停止也不能只靠缓存旧 PID 或找到一个 marker 就杀；选择保留的进程句柄/受管进程组或等效身份确认机制，拒绝 PID 复用和身份冲突。管理器控制的子进程树须有明确清理或接管结果。

### L4. 停止失败不能清预算或“假空闲”

- stop 先进入“期望停止”状态，阻止并发队列中的 start/上游 watchdog 自动复活；停止后只有新明确启动操作才可改变期望状态。
- 实例退出需要独立核验。部分失败、超时、权限拒绝时保留占位、错误与相关阻塞状态，禁止返回全 STOPPED。
- 不得在 stop 的 finally/尾部无条件清零失败预算；对其他角色的成功也不能解除失败角色的未结风险。
- 启动超时但进程仍活着，不等于可以再启。对已知进程做有界观察/清理，不再创建第二个。
- 恢复预算持续保存；三次同一自动恢复序列失败即 BLOCKED。unlock 不能是重试循环中的自动动作。仅协调者在完成明确离线修复、记录修复提交/回归证据、重新核对实例和未结失败后，可以显式申请一次有记录的恢复；缺少这些依据必须停止并报告。保留总尝试数，不把 unlock 当成清除历史。

### L5. 假进程测试与真实状态彻底隔离

当前假进程测试会 reset 生命周期状态。修复为独立临时 state/lock/log/marker 命名空间，显式 fake backend；不能读取真实凭证、真实 client 命令模板或写真实配额文件。真实环境存在时运行假测试也不得改变它的状态、预算或实例数量。

并发测试用多个 OS 进程，不仅多线程。故障注入先用轻量进程，通过后只做一套真实 Minecraft 的有限确认。普通 shell 权限没有因此变成操作系统沙箱；能配置外层 harness 时限制真实启动权限到唯一入口，不能配置则如实报告剩余权限边界，仍须撤除仓库内已知旁路。

## R1-C：停止的是导航任务，不只是按键

### C1. 统一收尾顺序

对 pause、cancel、成功结束、失败、超时、异常、lease loss、control loss、game session/world/dimension 变化以及明确授权的替换，统一处理：停止本执行继续调度 → 停止 Baritone 目标/路径任务及转向控制 → 释放移动/use/attack/sneak 等输入与破坏状态 → 按允许的恢复规则处理 cursor/Screen → 登记已发生效果及终态/待恢复状态。

不能把 `clearInputs()` 当作 Baritone cancel。也不要把库停止直接放进每 tick 的通用 clearInputs 导致正常导航每帧被重置。入口、终态和异常必须通过同一可审计的执行生命周期收尾。

暂停保留语义意图，不保留继续写键的路径进程；resume 对当前身份/目标重新验证再规划。新合法命令不自动意味着旧命令已收尾：无明确抢占授权不得替换仍活跃任务。

取消协议处理后 10 个 client ticks 内，不得继续生成新的业务动作。已经发出的包/惯性效果单独归账；有界 cursor 恢复只能是事先允许的收尾动作，不能继续原合成/卸货任务。跨屏/断线无法安全恢复时保留恢复债务与 unknown，不尝试朝新屏补点。

### C2. 导航能力约束

每次准入及会话切换验证禁止破坏/放置/自行调包/额外聊天入口等受控设置，不依赖只运行一次的 `constrained` 布尔。被篡改的设置要恢复并验证或拒绝执行；验证失败不得假装 constrained。不得直接开放 Baritone 自主采矿/探索。

`没有路径任务`、`规划失败/组件缺失`、`到达目标`是不同状态。不能用 `!isPathing()` 直接表示成功，也不能在计算阶段尚未进入 pathing 时每 tick 重发同一目标。可站位置与交互目标分开，树干等实心格不是站位；GoalNear/GoalBlock 的选择服从真实三维到达与准星要求，而不是某个固定类名。

修复能力检查中的实际动作名映射，尤其 `mine_opportunity`；缺组件须在副作用前拒绝。false/缺省 terrain permission 零挖零放；本轮 true 继续明确不支持，不新增挖穿权限。

## R1-I：真实共享事务，不能靠宽松后置条件凑成功

### I1. 共用 Screen 与槽位基础

先识别当前 screen/handler 的身份与角色，再从槽位归属映射玩家主包、快捷栏、容器等位置。不要把 `9/36` 和 `10/37` 两组常量套到所有容器；不确定的 handler 不写入。

玩家 2×2 在真实玩家背包界面/受验证的个人 Screen 事务中完成；外部界面打开时，不得 `setScreen(null)` 后假设服务端已回到个人 handler。正常关闭并等同步，或明确拒绝当前意图。

工作台/箱子/木桶必须绑定实际打开的目标及本次 Screen incarnation。仅 `CraftingScreen + syncId` 不足以证明它就是请求的那张工作台。已有错误容器、同类型另一容器、旧 sync-id 重用、game-session 改变都须拒绝旧计划。ownership 生命周期扩展现有机制，不另造绕过它的点击通道。

所有点击前重新验证目标、物品与 cursor 预期；等待实际同步与 revision/状态变化，不把固定 cooldown 经过当成确认。cooldown 可节流，但不能替代 ACK/状态证明。禁止出现负槽号、无空位就随便回退到 36、拿着未知物品继续点结果槽。

### I2. 固定增量语义与物品身份

物品移动 count 是本次移动量，不是目标槽最终至少有多少。例：目标已有 10 件，请求移动 7 件，合法完成是目标净增 7 件、源净减 7 件，不能原地返回完成。请求 0 要明确拒绝或单独无操作结果，不能混入成功转移统计。整堆语义须绑定所选源堆叠及其快照数量，多个源有歧义时不静默换对象。

组件/耐久/附魔等影响物品身份的属性须参与选择、合并、保护和结果证明。用户保护对象、被锁目标槽、任务最低保留量两侧都执行；不能仅比较 item ID。测试同 ID 两把镐必须实际移动指定那一把，并核验另一把仍在正确位置且组件未变。

至少覆盖主包↔快捷栏、精确 1/7/31 件、已有目标堆叠、溢出/满堆、普通箱子与木桶双向存取。复用同一移动/验证/收尾逻辑。仅需本轮范围，不做排序/物流平台。

### I3. 合成数量和原生路径

删除 `delta >= batches` 这类数量单位错误的放宽。请求新增 q、每批产出 p 时，以合法批次产生的实际数量和材料变化核验；正常完整完成应对应 `ceil(q/p)` 批及其合法产出，不是只比批次数。请求 32 木板只有 8 木板的结果必须拒绝 completed；未完成批次按已发生效果报告。

保留原生点击，不恢复 InventoryCrafting 服务端写包。配方必须由游戏实际结果验证，材料选择考虑全部批次和在场木种；至少橡木与第二树种按原计划成立。核心配方子集允许存在，不伪称万能合成。

验证材料消耗、产物真正入包、余料/光标/合成格状态以及本次操作链；初始已存在产物不能冒充新增。单看 remote completed 或类名字符串不能证明 native path。失败中已消耗的材料/已产出的物品不能隐去。

### I4. 精确放置与主体归因

指定物品、精确目标格及必要块状态；验证支撑面和预计落点。对应库存消耗必须参与判定，不是只写进 reason。物理点击回执、服务端正常处理事件或等效可信证据须能把效果与 Bob 本次动作关联。

测试他人抢先放入同类型块、其他类型块、目标相邻格被放块、Bob 没发有效交互等情况。仅目标格看起来正确不够。若多方并发使归因无法证明，返回已满足/冲突/unknown 等准确状态，不能声称 Bob 本次完成。完成或失败后停止客户端剩余重试，避免桥终态后继续放块。

### I5. 进食

食物在主包时通过共享事务调入手持，不能只给快捷栏食物测试。默认按已授权安全食物规则选择。核验本次正常使用/消费完成与物品真实减少、正常效果，不能用 `held.count < 64` 判断吃过，也不能仅用“食物减少 OR 饥饿增加”接受其他事件造成的变化。

自然饥饿/饱和变化可能与操作并发；不要机械改为另一个不可靠布尔公式。以本次物品使用链与效果为准，在受控 fixture 中作精确断言。无使用事件却减少物品、外部改变饥饿值、按键释放过早都不能假成功。消费一次即停止持续 use，不允许意外连吃。

### I6. 精确采集与有界恢复

`mine_opportunity` 始终关联原目标/方块 incarnation，不选最近同类替代。工具从主包真实调入；是否可空手及掉落遵循真实游戏规则。目标破坏和掉落拾取分别证明，目标消失但材料未入包不能完成资源获取。

A09/A10 在进入 G4 前独立实现并验证；不能再留到 G4 却预记 PASS。死亡/换世界/目标被他人取走/掉落不可拾取分别保留事实和未完成义务，不自动回放旧动作。

### I7. 未验收功能与回归

普通箱子/木桶存取、个人背包、工作台共用事务生命周期，未知角色/ghost 槽只读。已有 Tom’s deposit 不扩展，但重跑其原 ownership、双侧转移和保留工具回归。无法通过时不能删去该门。

本轮禁用未验收 smelt：能力查询不应宣称可用，分发和直接请求也拒绝。旧木器/铁器/夜守/up 脚本只能作为历史参考，不能旁路启动或与正式控制器竞争。
