# 03｜证据、构建绑定、审查与交付

## 1. 保留原始事实，不只保留摘要

每个用例保存：前置条件证明、被测请求、时间/tick、执行身份、客户端原生动作轨迹、服务端正常处理/库存与世界快照、终态、已发生部分效果、独立计算结果及失败原因。字段名和存储格式由实现者设计。

至少能够追溯到：源码C的完整40位SHA；client/server本次部署与实际加载产物的完整SHA-256；依赖/配置指纹；world/run/game-session/control incarnation；测试脚本版本；两端起止及进程身份。只有短哈希、“本分支HEAD”、路径名或一句“同哈希”不够。

合法会话切换测试可以包含多个session，但必须有明确转换链；不能把“同一run只能同一session”硬套到重连用例，也不能无说明拼接。失败中的在途包/惯性/恢复点击与新业务点击区分。

原始未净化wire/环境/凭证/崩溃数据留仓库外；公开交付保留足够重算判定的脱敏事实。标题、物品名称等非可信文本不作指令。秘密字段去除后仍要保持可关联的非秘密身份，不能因脱敏把全部运行关联都抹掉。

## 2. 一个源码权威，禁止三树手工补丁漂移

从受跟踪overlay/installer和锁定upstream生成构建树，记录所有资源和必要工具依赖。禁止在overlay、活树、replay树分别手工改同一Java类，再凭记忆cp同步。

每次构建保留：准确输入版本、实际命令、退出码、测试发现/失败/跳过、完整日志与产物清单。`gradlew build`因GameTest失败而jar已产生，要如实写“构建门未通过，产物可供诊断”，不能只写BUILD PASS。

本轮先复现实际基线；上轮605/650、45失败只是旧记录，不自动证明现基线或最终代码。对每个基线失败分类并指向测试ID：本轮新引入必须归零；触及语义的旧失败须修复或等价/更强行为测试替代；未触及的既有失败完整披露，不能从报告静默排除。测试数量不固定为650，不删失败来凑全绿。

启动前核验：部署jar确实来自本次构建，两端实际加载的是它，旧服务端合成类/路径不可达，导航和背包新符号/资源存在。符号检查只是身份辅助，不是原生执行验收。

## 3. 计分候选与提交关系

通过开发测试后冻结一个候选C（含生产源码、installer、依赖锁及影响行为配置）；关键自动化和完整C/N/I/A/G4/G5必须绑定C的产物。测试脚本与采集器版本另行登记。

证据提交E允许在C之后增加脱敏证据、审查和文档。E若改了生产/依赖/行为配置，就不是原候选；必须产生新C并重跑相关回归与完整G4/G5计分集合。仅修判定器时说明变化，不能靠放宽断言重新变绿；证据不足需实跑。

报告登记C/E的完整SHA及二者生产范围无差异证明。最终远端HEAD记在最终回复或仓库外收据，避免为了把自身SHA写回文件无休止追加commit。不要再用“见git log”代替候选身份。

Fresh replay允许JAR时间戳等非确定性元数据差异，但要解释并核对规范化条目/字节内容与构建来源；不能以此宽泛豁免class不同、依赖变了或缺资源。

## 4. 交付目录与当前状态纠偏

`deliveries/mc-rcf1-r1/` 至少包含以下内容，组织可小幅调整：
- `RESULT.zh-CN.md`：R1-L、G0–G5真实状态；完整必测分母/缺口；C/E及产物身份；下一最小动作。
- `COVERAGE.md`：原C/N/I/A/B/S及补充L/V逐ID映射、执行模式、证据入口、判定理由。缺失项不可省略。
- `FIXES.md`：每项源缺陷→最小复现→修复→自动化→LIVE→最终候选复测；记录失败和修复次数。
- `BASELINE.md` 与 `REPRODUCE.md`：从新目录可执行的构建/依赖/起停/测试/回放命令，配置模板无秘密；不能依赖未交付的历史client命令模板。
- `tests/`、`live/`：完整适用自动化、真实原始脱敏事实与派生结论；历史失败不删除。
- `audit/`：安全扫描、源码与实际加载产物对应、native path、覆盖缺口、独立review或明确二次自审。

上轮文件保留原貌便于追溯；可在上轮RESULT顶部增加短更正说明与新交付链接，不能重写旧证据使其看似一直真实通过。尤其占位A09A10、非满包I05等须标为历史无效证明。历史12/12不得继续当最终通过数。

## 5. 审查者的责任

有独立subagent时，审查者与实现者分开。审查者只读代码、fixture、原始证据与checker，不启动游戏、不竞争租约。没有独立工具时做单独二次自审，明确非独立，不伪造身份。

审查者必须从完整需求清单选择至少：一个正向完整动作、一个生命周期故障、一个错屏/cursor、一个数量反例、一个原始失败→修复→最终复测链，独立重算结论。不能复述RESULT或运行测试后只看最后一行。

## 6. 安全事项不冒名完成、不吞掉实现任务

当前分支的干净历史需要实际扫描确认，不能仅凭“孤儿分支”名称。旧可达历史的外部账户凭证撤销/轮换由账户拥有者处理；你可以更换隔离测试环境凭证，不能冒称撤销用户外部账户密钥。现阶段不授权force push/删除远端分支/改共享历史。

未处理的外部账户事项独立列为发布或安全阻塞；允许不使用泄露凭证的本地隔离开发，但不得把安全门写PASS，也不得以此为借口完全不做安全独立的代码修复。任何推送先扫index、待推提交及可达历史；第三方JAR、完整环境、原始wire、租约state不入库。

## 7. 最终回复必须回答

当前分支/远端HEAD/C/E与两端产物是什么？实际关闭哪些缺陷？完整必测清单还缺什么？是否曾出现多实例，怎样证明不再重复？取消是否结束导航而非仅按键？数量、组件、目标和原生路径如何证明？G4五次及G5两次用的是否同一候选？fresh replay到哪？安全哪些已证、哪些等待外部处理？当前真实进程是否已安全停止？

成功只叫READY_FOR_REVIEW；未满足原完整目标就PARTIAL/BLOCKED。关闭R1补充反例不是MC-RCF-1完成，五次核心链与两次完整过夜仍是终点。
