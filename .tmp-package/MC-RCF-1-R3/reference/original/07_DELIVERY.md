# 07｜交付与审查入口

## 1. 最终要交什么

新分支的完整可重建实现、适用自动化和 LIVE 证据、行为变更说明、缺陷/限制、final HEAD。不是只交一份实现建议，也不是只交“5/5 PASS”的结果摘要。

建议放在 `deliveries/mc-rcf1/`：

- `RESULT.zh-CN.md`：使用结果模板，开头直写结论与 G0–G5 状态。
- `DECISIONS.md`：导航选型、源码权威、增量语义、GUI/未知结果等关键实现决策。
- `REPRODUCE.md`：新目录构建、启动、运行自动化、fixture、LIVE、回放和清理的准确命令。
- `BASELINE.md`：审查快照、实际干净开发祖先、C/E 提交关系、依赖/环境/产物身份。
- `tests/`：自动化报告与测试发现清单，基线失败/新增修复/剩余问题。
- `live/`：脱敏的 C/N/I/A/B/S 组证据；每个用例指向请求、状态快照、回执和结果。
- `audit/`：范围、安全、源码与产物映射、native path、独立审查或二次自审说明。

目录可合理调整，保持入口清楚，不为目录格式浪费实现时间。日志/原始资料必须经过实际脱敏后才可提交；第三方二进制不入库。

## 2. 报告必须回答

1. 你测试的是哪个 commit、哪些 jar、哪个世界/会话？干净开发祖先如何确定？
2. 导航用了什么组件/版本，后台输入隔离与取消如何验证？
3. Real Client 服务端合成捷径是否确实不可达？原生 2×2/3×3 证据在哪里？
4. 主包食物/工具/方块怎样真实进入快捷栏？怎样避免错槽与组件串换？
5. 放置、合成、进食、采集的成功分别怎样证明？哪些错误不能叫 completed？
6. 参数错误是否仍抢占无关动作？重复请求、断线、cursor 与未知效果怎样处理？
7. `allow_terrain_changes=false` 和不支持的 true 实际行为是什么？
8. G4 五次矩阵与所有失败尝试是什么？最终候选有没有中途变化？
9. G5 两次是否真的完整过夜、在线无死亡并保有进度？谁在做决策？
10. fresh replay 是否从零重建并再次通过关键 LIVE？哪些旧测试被合法替换？
11. 哪些能力只是实验/不支持？smelt、铁器和其他时代脚本是否从本轮入口禁用？
12. 安全处理哪些已验证、哪些仍等账户拥有者？是否有未发布本地交付？

不得复制旧 0.8 的测试计数、attestation 或 FROZEN 结论填空。

## 3. 可复核结果

测试汇总必须由实际日志生成；空列表、缺证据、未知结果或 mixed-run 不能默认通过。每个必需用例有 PASS/FAIL/BLOCKED/NOT_RUN 与解释。

既可保留游戏世界调试副本，也可交短视频/截图帮助理解，但它们不能代替程序状态、物品与原生交互路径证据。禁止为了提供视觉材料而让用户手动运行游戏。

## 4. 终态规则

- 所有必需门通过且发布安全/证据完整：`READY_FOR_REVIEW`。
- 基础机械 G0–G4 通过但 G5 未过：`PARTIAL — native foundation passed; overnight loop incomplete`，不得宣称已稳定生存。
- 导航、原生合成或安全边界存在未解决核心问题：`BLOCKED`，附最小复现与复用方案评估。
- Agent 完成不是正式接受。提交后不继续在该候选上扩展铁器任务；由下一次独立审查确定是否接受。全部通过也只证明本轮限定的基础动作与两个过夜场景，不证明已经能通关、兼容任意模组或长期无人值守。

## 5. 精简最终回复格式

先给结论，再给分支/HEAD、G0–G5、关键指标、阻塞和复现入口。没有工具支持的“独立 reviewer”“全绿”“密钥已轮换”“已推送”不得出现。

需要用户处理的真正外部依赖集中说一次；普通实现决策不要作为问卷抛给用户。
