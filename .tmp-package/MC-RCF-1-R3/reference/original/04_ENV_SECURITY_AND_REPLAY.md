# 04｜环境、凭证与可重建交付

## 1. 审查快照不等于干净开发祖先

制作计划包时确认：`experiment/mc2a0-8r1-acceptance-closure` 指向 `61aa6a85296d5722a80fc935bcc6ca53bf8bfec5`。本轮用它理解最新代码，不能把旧 0.8 任务包直接应用到它。

开工时再次刷新。若有新提交：记录差异；仅有与本轮无关的文档可以继续以本包快照为审查基准，代码/协议差异必须盘点。不要无提示切到 master，也不要覆盖已经存在的同名新分支。

当前历史中出现过“凭证被 push protection 拦截后脱敏”的提交说明，`.build/play-lease-state*.json` 也被跟踪。此包没有证明那些凭证有效，也没有证明它们已被全部撤销。

安全流程：
1. 本地扫描工作树、index、待发布提交及其可达历史，检查凭证/租约状态、原始 wire 日志、第三方二进制和不应公开的文件。扫描结果只输出路径、类别和必要指纹，不输出秘密全文。
2. 已实际暴露的可用凭证应优先撤销/轮换。Agent 可以生成并替换隔离测试环境自己的 bridge/control token；没有明确权限时不得擅自改用户外部账户凭证。需要账户拥有者处理的事给出最小阻塞说明，不能声称代为完成。
3. `.build`、`.secrets`、运行日志、租约状态、下载 JAR、崩溃 dump 等不再跟踪。删除当前文件不能作为历史已清理的证明。
4. 若 `61aa6a…` 的祖先含未清理秘密，不要把它们带到新工作分支。可在独立本地目录，从实际扫描确认的干净祖先创建新分支，只提取并脱敏所需代码变化；记录旧路径/版本到新代码的映射。`f074eb90…` 只是检查候选，不是无条件安全值。
5. 不允许自动对共享历史 force push、删除远端分支、绕过 push protection 或公开含问题的 patch。共享历史清理另列操作与授权需求。
6. 必须保留用户本地原有工作，不做不加区分的 reset --hard、git clean 或整目录删除。备份也不得进入公开仓库。

若外部账户安全处置暂不可由 Agent 完成，可以继续用新生成的本地凭证做隔离源码开发和测试；不得使用已知泄露凭证、不得发布含问题历史、不得把安全门写成 PASS。最终交付明确区分“实现完成”和“公开发布/账户处置被阻塞”。这不是让整个任务退化成只讨论历史审计。

GitHub 官方处置说明作为背景列在 `06_SOURCE_AUDIT.md`；本页规定的是本轮具体操作边界。

## 2. 世界和进程隔离

- 生产世界和现有游玩进度默认只备份、不改动。不删除世界、不清玩家数据，不把测试物品带回生产档。
- 新建本轮专用 server/client/run 目录；端口与 production 分离或停掉明确归属本项目的旧实例。所有起停动作保存 PID/启动标记，不按 java.exe 名字批量杀进程。
- 固定 Minecraft、Fabric Loader/API、Java、各 mod 与配置。测试时关闭任何会用服务器写数据代替 Bob 动作的捷径。
- G0 记录各实际端的 jar 哈希和启动身份；客户端与服务端共同组件版本必须兼容，不只记录源码 SHA。
- 自动重连可以恢复连通性，但不等于恢复正在进行的业务；必须重读身体、世界、背包、GUI 和未决执行后 reconcile。

## 3. Fixture 与真实游玩的分界

允许测试装置在 **run armed 之前** 建立隔离测试世界、布置障碍、安排指定库存、设置起始时间/位置/天气、恢复 fixture。必须记录配置和使用目的。

一旦本次计分运行开始，控制器不能用 RCON/命令/服务端写入补救。G4/G5 的空背包核心链尤其不能中途给木材、工具、工作台、食物或恢复存档。

特定负例需要外部 actor 改动通路/目标时，作为用例事前定义的注入事件记录，不能用来推动本该由 Bob 完成的成功流程。

服务端测试 observer 可以只读核验世界差异、物品与回执，但与 LLM/Body 决策通道隔离。禁用拿 `/locate`、墙后库存、seed 地图等“只读”结果给 Bot 决策的路径。计分模式不暴露通用 RCON/任意命令工具给游玩控制器；所有测试管理员调用单独留审计轨迹，证明没有在 run 内补救。

每次 run 都有锁定初态、源码候选、配置、开始和结束标记。半途 reset、换 jar、修改生产代码会使该 run 失去成功资格，而不是重置计时继续算同一次。

## 4. 可重建源码

当前 README 表明 `D:/code/mc-experiment/aibot` 是活工作区，`mc-bot` 同时承担 overlay 与工具。G0 要找出实际编译源，不能只修档案副本却测试另一棵树。

本轮不强制做仓库大搬家，但要满足：
- 一个明确的源码权威路径；upstream commit + 本仓库跟踪的 overlay/patch/installer 能生成完整 build tree。
- 所有本轮必要 Java/Mixin/resources/build/工具变化都能从 Git 重放，不依赖上一台机器的未提交源码。
- `play.py` 等必要依赖不再只能从历史实验目录 import；路径通过配置或包内定位。配置样例不含密码。
- 依赖来自官方来源，有固定版本、源码 ref、下载地址和 SHA-256；下载 JAR 放仓库外/被忽略缓存，不提交。
- 许可证与再分发要求由实现者阅读对应版本原文并记录处理，不将第三方代码来源隐去。
- 实际下载摘要与官方/锁文件不一致时停止使用该资产，不能无说明刷新摘要“让测试绿”。

## 5. Fresh replay

从全新目录执行，不复用活工作区里的 class/jar/临时补丁：
1. 取最终候选 commit 及锁定 upstream。
2. 重建源码树；记录重放过程与意外差异。
3. 获取并校验依赖，完整构建。
4. 跑适用的现有与新增自动化，不能只编译。
5. 部署到新 run 目录，重新验证源码→产物→实际运行身份。
6. 重跑一个完整 G4 核心链，以及取消、原生 GUI/无工作台负例。

确定性源码、资源和依赖必须一致；若 JAR 本身含构建时间等非确定性元数据，说明差异来源，比较规范化内容/类资源与构建来源。不能虚报 byte-identical，也不能以正常时间戳为由放弃源码重放。

## 6. 发布边界

实现/测试/证据分离提交便于审查，但不强制恰好 A/B/C/D 四笔。改动先扫描再提交；推送只允许新分支且通过所需安全检查。

源码最终候选为 C，证据提交可以为 E。报告记录 C 和 E 的关系及代码/资源无变化证明；E 若又改了生产源码/依赖/配置，原测试不能继续证明 E 的新行为。

最终 HEAD、远端匹配和工作树状态在全部提交结束后核对。需要 final attestation 时生成在仓库外，避免“为了把自己的最终 SHA 写进去又追加提交”的循环。旧 0.8 attestation 不能替代本轮审计。
